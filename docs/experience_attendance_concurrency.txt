======================================================
  출석 기능 개발 경험 정리
======================================================

어디서: 교내

무엇을: 스터디룸/동아리 관리 플랫폼(COMA ROOM) 백엔드의 출석 기능 개발

누구와: 팀원 6명과 함께


------------------------------------------------------
  어떻게 (기술 스택)
------------------------------------------------------

  - Spring Boot 4.0.1 / Java 25
  - Spring Security + JWT (인증/인가)
  - JPA (Hibernate) + MySQL (출석 데이터 영속화)
  - Redis (QR 코드 ID ↔ 이벤트 ID 임시 저장, TTL 적용)


------------------------------------------------------
  어떤 문제
------------------------------------------------------

학교 출석 시스템을 참고하던 중, 기존의 출석 번호 방식에서 보안 허점을 발견했다.
번호만 알면 실제로 현장에 없어도 출석이 가능했기 때문에,
누군가 번호를 공유하면 대리 출석을 막을 방법이 없었다.

같은 방식으로 구현하면 우리 플랫폼도 동일한 문제가 생길 것이 분명했다.

그리고 실제로 QR 출석을 구현하고 팀원들과 테스트했을 때,
출석 완료 응답(200 OK)은 정상적으로 반환됐지만 DB에 반영되지 않는 케이스가 발생했다.

또한 여러 명이 동시에 출석 요청을 보낼 때 일부 요청이 유실되는 동시성 문제도 확인했다.
여러 트랜잭션이 같은 데이터를 동시에 수정하면서 서로의 변경사항을 덮어쓰는 상황으로,
현재 해결 방법을 고민 중이다.


------------------------------------------------------
  어떻게 해결
------------------------------------------------------

[문제 1 - 대리 출석 방지]

출석 번호 방식 대신 QR 코드 방식으로 전환했다.
관리자가 이벤트 시작 시 QR을 생성하면, 해당 QR의 ID를 Redis에 짧은 TTL과 함께 저장한다.
현장에서 QR을 직접 스캔해야만 출석이 처리되므로, 번호 공유를 통한 대리 출석이 불가능하다.

[문제 2 - DB 미반영]

EventParticipant를 Event 엔티티의 컬렉션을 통해 간접 저장하는 방식에서
EventParticipateRepository를 통해 직접 저장(save)하는 방식으로 변경했다.
추가로 (event_id, member_id) 복합 유니크 제약을 걸어
동일 멤버의 중복 출석 요청이 들어와도 DB 레벨에서 하나만 통과하도록 방어했다.

  [변경 전]
  event.addParticipant(currentUser);

  [변경 후]
  EventParticipant participant = EventParticipant.builder()
          .event(event)
          .participantMember(currentUser)
          .build();
  eventParticipateRepository.save(participant);

[문제 3 - 동시성 문제] (미해결)

여러 명이 동시에 출석 요청을 보낼 때 일부 요청이 유실되는 문제는 아직 해결하지 못했다.
낙관적 락(Optimistic Lock), 비관적 락(Pessimistic Lock), Redis 분산 락 등
여러 방법을 검토 중이다.


------------------------------------------------------
  배운 점
------------------------------------------------------

기존 시스템의 문제점을 먼저 파악하고 설계에 반영하는 것이 중요하다.
편리한 라이브러리나 프레임워크 기능도 동시 요청 상황에서는
예상치 못한 방식으로 동작할 수 있으므로 검증이 필요하다.
